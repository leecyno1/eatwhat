# EatWhat V2 — 四模块完整产品方案（用户视角 + 技术栈 + 编码逻辑 + 任务列表）

> 目标：当用户“此刻想吃但不知道吃什么”时，用最少交互给出最优解，并把“决策→执行→反馈”做成可持续变强的闭环。
>
> 你当前的四模块规划（我按产品闭环重命名）：
> 1) **VR 首屏**：偏好元素气泡库（仪式感 + 快速收敛偏好）
> 2) **LLM 决策**：大模型推理生成“推荐菜品集合”（含图片/搭配/占卜）
> 3) **执行与导流**：自制菜谱 / 到店（点评）/ 外卖（美团/饿了么）三路径落地
> 4) **持续个性化**：收藏 + 反馈学习 + 历史复用 + 指标/增长闭环

---

## 1. 如果我是用户：我需要的“完美解法”是什么

### 1.1 用户当下的真实问题
- **不是“随机”**，而是“在时间/预算/体力/心情/健康约束下，快速做决定”。
- 结果必须 **可执行**：我点完就能做/能去/能点外卖，而不是只给灵感。

### 1.2 体验原则（决定你会不会被反复打开）
- **10 秒内给一个“我愿意点”的答案**：默认一键模式，不强迫填问卷。
- **少打扰但更懂我**：用“微反馈”学习（喜欢/不喜欢/跳过/收藏/最终选择）。
- **每次都像为我定制**：同样标签也要有多样性（MMR/探索）。
- **结果页就是行动页**：同屏给出菜图、卡路里、时间、路径按钮（做/去/点）。

## 2. 四模块的产品设计（完整 UI/流程）

### 模块 1：VR 首屏（偏好气泡库 + 仪式感）

**核心目标**：用 3–8 次轻交互，收敛“此刻偏好向量 + 硬约束”，并让用户觉得“爽、准、有趣”。

**页面结构（建议）**
- 顶部：当前“约束胶囊”（时间/预算/人数/是否能做饭/忌口/健身目标），可一键编辑。
- 中部：**气泡场**（随机出现 + 收藏必出现 + 根据使用习惯偏移）。
- 底部：两个 CTA：
  - `一键推荐`（默认，无需选满）
  - `进入老虎机`（仪式感更强：选 3–7 个偏好后触发）

**交互建议（对齐你现有设计）**
- 点选：加入“本轮偏好篮子”
- 长按：展示“示例菜 + 口味/热量/耗时”预览
- 上滑/下滑：喜欢/不喜欢（写入学习信号）
- 双击：锁定（本次一定参与推理）

**100+ 偏好实体库（落地方式）**
- 每个偏好元素 = `tagId + label + visualSpec + effectKey`
- visualSpec 建议数据化（颜色、形状、icon、粒子、动效强度），避免写死在代码里

---

### 模块 2：LLM 决策（大模型推理生成推荐菜品）

**核心目标**：把“标签 + 用户画像 + 统一菜谱库”融合成高质量推荐；让 AI 做“解释与创造”，让本地引擎保证“稳定与离线”。

**两阶段架构（强烈建议）**
1) **本地召回/排序（稳定、离线可用）**
   - 从 `unified_recipes.db` 召回 50–200 道候选（FTS + 标签过滤 + 硬约束过滤）
   - 用推荐引擎（可解释打分 + MMR 多样性）排序得到 TopK
2) **LLM 精排/补全（更懂你、可生成内容）**
   - 输入：TopK 候选摘要 + 用户本轮偏好 + 历史偏好/忌口/预算/时间
   - 输出：Top3–9 的最终推荐 + 解释 +（可选）替代方案

**结果表现**
- 卡片瀑布/轮播：菜图（AI 或库图）+ 关键标签 + 热量/时长/难度
- “搭配气泡”浮层：饮品/酱汁/主食/配菜，点一下加入本次方案
- “趣味占卜”按钮：不强制出现，作为增强体验的分支

---

### 模块 3：执行与导流（做 / 去 / 点）

**核心目标**：把“推荐”变成“成交/行动”，并且让用户觉得省心。

#### 3.1 自制（Cook）
- 使用统一菜谱库：步骤/食材/用量/替代品/器具/计时器
- 额外：一键生成“本地化菜谱变体”（根据人数、口味强度、是否少油少盐调整）

#### 3.2 到店（Dine-in）
- 优先策略：**不接重 API 先跑通** → 用 `大众点评/高德/Apple Maps` 的搜索深链
- 输入：菜名 + 城市/定位 + 关键词（“招牌/必点/评分高”）
- 输出：餐厅卡片（名称/距离/人均/评分）+ `打开点评` + `导航`

#### 3.3 外卖（Delivery）
- 同样优先深链：美团/饿了么搜索页；没有 App 则打开 Web
- 你仓库里已有导流基础：`PurchaseLinkService` + 渠道选择 UI（旧链路），建议迁移到 V2

---

### 模块 4：持续个性化（收藏/学习/复访/增长）

**核心目标**：越用越准、越省时间，并形成可运营的闭环。

**用户侧**
- 收藏：偏好标签 / 菜品 / 菜谱变体 / 餐厅 / 外卖店
- 历史：按“场景”自动归档（夜宵/健身/加班/聚会）
- 一键复用：`上次吃得很爽`（直接复现上次的约束 + 偏好篮子）

**系统侧**
- 偏好学习：将“选择/收藏/完成/跳过/不喜欢”转成权重更新
- 探索/利用：ε-greedy 或 Thompson，控制惊喜与稳定的平衡
- 指标：决策时长、推荐点击率、执行转化（做/去/点）、收藏率、复访率

## 3. 技术栈（基于你当前工程的最短可行路径）

### 3.1 客户端（Flutter）
- UI：Flutter + Flame（气泡物理/粒子/动效）
- 状态：先维持现状，新增模块用单一范式（建议逐步迁移到 Riverpod 或继续 Provider，但要统一）
- 持久化：
  - 统一菜谱库：SQLite（`unified_recipes.db`，FTS5）
  - 用户侧数据：SQLite（收藏/历史/事件）或 Isar/Hive（二选一，建议 SQLite 统一）
  - 轻量配置：SharedPreferences（AI 配置、开关）

### 3.2 AI 服务层（可插拔）
- 文本生成：OpenAI 兼容 `chat/completions`（你现有 SiliconFlow/Qwen 可用）
- 图片生成：OpenAI 兼容 `images/generations`（参考 `what-to-eat` 的实现方式）
- Prompt 模板化：分模块（推荐/搭配/占卜/菜谱变体/营养分析）
- 动态配置：参考 `what-to-eat` 的 settings store → Flutter 侧做“运行时可改 API/模型/温度/超时”

### 3.3 导流/第三方
- **你已选择“直接对接官方开放 API”**：需要申请资质、拿到 AppKey/Secret/Token，并严格按官方文档做签名/鉴权/限流/合规。
- 实现策略：在 App 内保持 Provider 抽象（Meituan/Eleme/Dianping），后端可选（纯客户端直连或自建中转服务）；推荐先把接口封装好，等密钥与文档齐全后再填充真实 path/参数/解析逻辑。

## 4. 编码逻辑（系统分层与数据流）

### 4.1 统一领域模型（建议以 dish 为核心）
- `Dish`（菜品概念）是主实体：推荐/收藏/执行都围绕 `dishId`
- `RecipeVariant`（来源变体）：HowToCook/下厨房/AI 生成
- `Tag`：既是“偏好元素”也是“检索/推荐信号”
- `Pairing`：搭配（饮品/酱汁/主食/配菜）

### 4.2 推荐引擎建议采用“召回→排序→LLM精排”
- 召回：FTS（菜名/食材/标签）+ dish_tag 精确过滤 + 硬约束过滤
- 排序：复用你现有 `RecommendationEngine V2` 的思想（可解释 + MMR）
- LLM 精排：只看 TopK 候选摘要，避免“凭空生成”且降低 token/成本

### 4.3 执行路径是“同一个 dish 的不同落地”
- Cook：落到 RecipeVariant（优先 HowToCook，其次下厨房，再 AI 补全）
- Dine-in：`dishName + location` → 大众点评/美团开放 API → 餐厅列表（评分/距离/人均）→ 打开下单/导航
- Delivery：`dishName + location` → 美团/饿了么开放 API → 门店/商品列表（时效/距离）→ 下单

> 重要：不做逆向/抓包/爬取私有接口；仅对接官方开放平台 API（需要资质与授权）。
