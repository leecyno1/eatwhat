# 项目开发规则文档

## 1. 语言要求
- 所有回复使用中文
- 代码注释使用中文
- 文档标题和说明使用中文

## 2. 技术构建规范
- 编写程序涉及环境构建及技术栈构建时，先用context7（mcp）更新最新的库和示例
- 确保代码方案及代码为最流行的
- 使用当前最新的稳定版本依赖包
- 遵循行业最佳实践

## 3. 开发流程与交互
- 项目启动前，需与用户进行必要交流
- 评估项目的类型、定位、复杂度、技术栈
- 按标准开发流程形成完备的开发方案
- 每个开发阶段都要有明确的里程碑

## 4. 大型项目处理
- 若评估为大型项目，开发方案需拆解为独立子模块
- 每个模块完成开发、测试、优化且运行无误后，再进行下一模块开发
- 模块间要有清晰的接口定义
- 保证模块的独立性和可测试性

## 5. 角色适配
- 考虑到用户为项目策划，底层代码编写能力较差
- 需清晰自身角色进行互动
- 提供详细的技术说明和决策依据
- 主动承担技术实现责任

## 6. 项目文档管理
项目开始时所有项目要建立5个文件：

### 6.1 开发方案相关文件 (DEVELOPMENT_PLAN.md)
- 作为参考的规则文档
- 技术栈选择和架构设计
- 开发时间规划

### 6.2 项目进程记录文件 (PROJECT_JOURNAL.md)
- 累加记录项目开发过程中的所有过程
- 便于查看和回溯
- 记录重要决策和变更

### 6.3 项目bug及解决文档 (BUG_TRACKER.md)
- 将测试和用户反馈的bug和解决方案进行记录
- 便于后续查看
- 包含复现步骤和解决方案

### 6.4 用户指令文档 (USER_COMMANDS.md)
- 历史用户所有的提问和命令都要保存在该文档
- 便于理解用户需求变化
- 追踪需求演进过程

### 6.5 本规则文件 (PROJECT_RULES.md)
- 不更新的基础规则文档
- 作为开发指导准则

### 6.6 文档更新策略
- 每次开启新一轮对话时，要检查这几个文件
- 分析当前动作是否需要调整
- 每轮对话结束要在原有基础上更新这几个文件

## 7. 效率与测试工具
### 7.1 工具使用授权
- 所有操作性的东西都充分授权给AI
- 尽可能使用各类mcp工具包括：
  - desktop
  - fetch
  - firecrawl
  - playwright
  - Xcode
  - sequencial thinking
  - context7
  - figma
  - magic
  - pandas
- 提高效率，减少用户负担，减少确认事项

### 7.2 浏览器自动化
- 尽可能控制Chrome浏览器执行网站登录、注册、配置、内容识别及反馈等操作
- 自动化测试和验证流程

## 8. 环境部署管理
- 因涉及多项目并行开发和使用
- 环境部署时尽量优先采用anaconda、docker等版本管理工具
- 建立部署环境以避免版本冲突
- 保证环境的可复现性

## 9. 测试与质量保证
- 所有开发到完成阶段时自行测试
- 不要拿半成品让用户测试
- 更不要构建虚假数据来应付
- 确保交付质量，避免后期问题
- 进行充分的单元测试和集成测试

## 10. 开发原则
- 优先编辑现有文件，而非创建新文件
- 除非绝对必要，否则不创建新文件
- 不主动创建文档文件（*.md）或README文件
- 只在用户明确要求时创建文档文件
