# 《吃什么》项目开发规范 (Cursor Rules)

## 📋 基础规则

### 1. 沟通规范
- **语言要求**: 所有对话和文档使用中文
- **角色分工**: 项目策划者(需求方) + 全栈开发工程师(技术方)
- **交流方式**: 需求驱动，技术方案先讨论后实施

### 2. 技术栈管理
- **信息获取**: 环境构建时必须使用MCP工具获取最新库信息和示例
- **版本管理**: 优先使用conda、docker等版本管理工具
- **依赖更新**: 定期检查和更新项目依赖包

## 🏗️ 项目架构

### 当前项目信息
- **项目类型**: Flutter跨平台美食推荐应用
- **技术栈**: Flutter 3.x + Provider + Hive + Dio + AI推荐
- **复杂度**: 中等（包含气泡交互、智能推荐、外卖集成）
- **开发阶段**: 第一阶段基本完成，进入优化扩展阶段

### 模块划分
```
lib/
├── core/           # 核心业务逻辑
├── features/       # 功能模块
├── shared/         # 共享组件
└── main.dart       # 应用入口
```

## 📋 开发工作流程

### 阶段一：项目启动
1. **需求分析** → 明确功能范围和优先级
2. **技术方案** → 选择合适的技术栈和架构
3. **环境准备** → Docker/Conda环境配置
4. **基础搭建** → 项目骨架和核心模块

### 阶段二：模块化开发
1. **功能拆解** → 大功能分解为独立子模块
2. **单模块循环**:
   - 开发 → 测试 → 优化 → 验证通过
   - 只有当前模块完全稳定后才开始下一个
3. **集成测试** → 模块间兼容性验证
4. **性能调优** → 针对瓶颈进行专项优化

### 阶段三：测试部署
1. **自动化测试** → 使用MCP工具进行Chrome自动化测试
2. **用户体验测试** → UI交互和性能验证
3. **部署准备** → 构建和发布流程
4. **文档维护** → 更新用户手册和技术文档

## 🛠️ 技术开发规范

### 环境管理
- **Flutter版本**: SDK >=3.4.4
- **包管理**: 优先使用stable版本
- **容器化**: Docker开发环境
- **版本控制**: Git分支策略(main/develop/feature)

### 代码规范
- **目录结构**: 遵循Flutter标准结构
- **命名规则**: 驼峰命名，类名大写开头
- **注释标准**: 业务逻辑必须中文注释
- **性能标准**: 遵循Flutter最佳实践

## 📚 文档管理

### 文档体系
1. **开发记事本** → 按日期记录进度(`PROJECT_JOURNAL.md`)
2. **技术文档** → API、数据模型、架构设计
3. **用户文档** → 安装、使用、配置指南
4. **测试文档** → 测试计划、结果、性能报告

### 更新规则
- 每日更新开发记事本
- 重要决策和变更必须记录
- 问题解决方案要详细记录
- 性能优化结果要量化记录

## 🔧 MCP工具使用策略

### 浏览器自动化
- **UI测试**: playwright/puppeteer自动化测试
- **性能分析**: Chrome DevTools调试
- **用户流程**: 登录注册自动化验证
- **内容验证**: 页面元素识别和交互

### 开发效率
- **代码生成**: 样板代码自动生成
- **依赖管理**: 自动检查更新
- **监控集成**: 实时性能监控
- **文档生成**: API文档自动化

## 🎯 项目特定规则

### 《吃什么》应用专项
1. **气泡交互优化** → 流畅度和响应性能
2. **AI推荐算法** → 准确性和个性化
3. **外卖平台集成** → API稳定性和数据准确性
4. **跨平台适配** → iOS/Android一致性

### 开发优先级
1. **核心功能稳定性** > 新功能开发
2. **用户体验** > 技术复杂度
3. **性能优化** > 功能扩展
4. **代码质量** > 开发速度

## ⚡ 效率提升原则

### 简化流程
- 减少手动操作，优先使用自动化工具
- 标准化常用操作，建立模板和脚本
- 重复性工作交给MCP工具处理

### 质量保证
- 每个模块必须有完整的测试覆盖
- 性能指标必须量化监控
- 用户反馈要及时收集和处理
