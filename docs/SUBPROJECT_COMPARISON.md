# 子项目对比：HowToCook vs what-to-eat vs 当前 eatwhat（结论版）

> 目标：用最短的话说明两个子项目“各自能贡献什么”，以及和当前 Flutter 主项目（尤其 V2）相比的差异与集成结论。

## 1) HowToCook（程序员做饭指南）

### 核心资产
- **高密度菜谱语料**：大量 Markdown 菜谱，按目录/难度/分类组织，适合作为“自制菜谱库”的数据源。
- **结构相对稳定**：字段不统一但可通过 builder 解析为结构化数据（标题/食材/步骤/难度等）。

### 与当前项目的关系
- 当前仓库已经存在 HowToCook 导入/增强的产物与脚本（如 `howtocook_*_recipes.db`、相关 builder/log/report）。
- 作为 **unified_recipes.db** 的一类 `recipe_variant.source`（HowToCook 变体），适合承载：
  - “自制”路径的做法/步骤（离线稳定）
  - “做法/技法/难度”维度的标签化基础

### 局限
- **不提供“生成”能力**：它是内容库，不是推荐/生成系统。
- 图片/评分/收藏等用户侧数据天然缺失，需要后续补全或通过其他源融合。

## 2) what-to-eat（一饭封神）

### 核心资产
- **AI 生成工作流**（可直接借鉴到 Flutter）：
  - 文本：`/chat/completions` 生成菜谱 JSON（严格格式 + 清洗 ```json``` 包裹）
  - 图片：按菜名+食材拼提示词，调用图片生成 API 输出成图 URL
  - 扩展：酒水搭配、酱汁设计、营养分析、趣味占卜（组件/提示词模式明确）
- **动态配置体系**：运行时可切换 baseUrl/apiKey/model/timeout/temperature（用 store + utils 封装）。
- **收藏体系**：基于 localStorage 的轻量收藏（Recipe 整体入库，带备注、统计）。

### 与当前项目的关系
- 当前 Flutter 工程已经有：
  - `flutter_dotenv`（env 注入）
  - `dio`（网络请求）
  - `shared_preferences`（本地轻量持久化）
  - V2 已有 `AiService` + `V2FavoritesService` 的雏形
- 结论：what-to-eat 更像“模块 2（生成）”的参考实现，尤其是：
  - **提示词构造**（输出 JSON、容错解析）
  - **图片生成提示词**（菜品摄影风格、画面约束）
  - **动态配置 UI**（把 AI 配置从 `.env` 升级为用户可调）

### 局限
- Web 项目更偏“表单/卡片流”，交互不等同于 V2 的“气泡 + 老虎机”，需要重新 UI 化。
- 生成内容为主，缺少离线统一底座库；对“真实性/稳定性/可检索”不如 unified DB。

## 3) 当前 eatwhat（Flutter 主项目，V2 为主线）

### 现状优势
- **强交互入口（V2 模块 1）**：气泡偏好选择 + 老虎机决策，适合“选择困难”场景的第一触点。
- **统一底座（unified_recipes.db）**：可离线召回/检索/展示，稳定可靠（适合作为“核心之一”）。
- **多路径执行设计**：自制/到店/外卖，契合“从决定到行动”的闭环。

### 当前关键差距（相对两个子项目）
- 标签系统需要从“硬编码 UI 标签库”向“DB 词典 + UI 视觉映射”过渡（保证可扩展与一致性）。
- 模块 2（生成）需要补齐：
  - 统一的提示词/JSON 解析策略
  - 图片生成能力的服务层封装与缓存
  - 动态配置/密钥管理（避免把 secret 放客户端）
- 模块 3（外卖/到店）需要走合规方案：
  - 优先 openH5/官方承载（或跳转到官方 App）
  - 避免逆向抓包/私有接口“挖掘”

## 4) 综合结论（怎么用它们，才最强）

- HowToCook：作为 **“确定做什么之后 -> 自制”** 的确定性内容底座；继续用于统一库增量与标签沉淀。
- what-to-eat：作为 **“想象力与生成能力”** 的参考实现；把它的“生成菜谱 JSON / 图片提示词 / 动态配置 / 收藏”模式移植到 Flutter 的模块 2/4。
- eatwhat：把 V2 的强交互入口与统一库结合，形成“离线稳定 + 在线增强”的双引擎：
  - 离线（统一库召回/筛选/展示）
  - 在线（大模型生成/补全/图片/搭配/占卜）
